# CS2 GSI 能力清单

本文件整理 CS2 官方 Game State Integration（GSI）能提供什么、我们能从中推出什么，
以及明确做不到什么。它是 M2 全部任务的设计依据。

信息来源：
- Valve 官方文档 https://developer.valvesoftware.com/wiki/Counter-Strike:_Global_Offensive_Game_State_Integration
- M2-T1 在 CS2 休闲模式下录制的 119 条真实 payload

---

## 一、数据组：哪些对普通玩家有效

配置文件的 `data` 段决定游戏推送哪些内容。以下按"普通玩家能不能拿到"分类。

### 普通玩家可用

| 数据组 | 内容 | 我们是否已请求 |
|---|---|---|
| `provider` | 游戏名、appid、本机账号 steamid、版本、时间戳 | 是 |
| `map` | 地图名、模式、比赛阶段、双方比分、连败数、剩余暂停 | 是 |
| `map_round_wins` | **每一回合的获胜方式历史** | **否，建议补上** |
| `round` | 回合阶段、炸弹状态、回合获胜方 | 是 |
| `player_id` | 当前描述对象的 steamid、名字、战队标签、观察者槽位、队伍 | 是 |
| `player_state` | 血量、护甲、头盔、被闪、烟雾、燃烧、金钱、装备价值、本回合击杀数与爆头数、拆弹器 | 是 |
| `player_weapons` | 所持武器列表：名称、类型、弹夹、备弹、是否手持 | 是 |
| `player_match_stats` | 全场击杀、助攻、死亡、MVP、评分 | 是 |

### 仅 GOTV / 观察者可用（普通玩家拿不到）

| 数据组 | 内容 | 说明 |
|---|---|---|
| `allplayers_id` / `allplayers_state` / `allplayers_match_stats` / `allplayers_weapons` / `allplayers_position` | 全场每个玩家的完整数据 | 需要真正的观察者身份，死亡观战不算 |
| `phase_countdowns` | 回合剩余时间、炸弹倒计时、冻结时间倒计时 | **我们拿不到，回合内计时必须自行实现** |
| `allgrenades` | 所有手雷与火焰的位置、类型、速度 | |
| `player_position` | 当前观察对象的位置与朝向 | |
| `bomb` | 炸弹的位置、携带者、是否掉落 | 注意：炸弹的**状态**（安放/拆除/爆炸）在 `round` 组里，普通玩家可得 |

## 二、关键机制

### 死亡观战时数据主体会切换（已实测确认）

玩家死亡后观战队友时，`player` 段整体切换为**被观战队友**的数据：
steamid、health、round_kills、active_weapon 全部跟随队友。

**因此任何涉及 player 字段的判断都必须先比对 `player_id.steamid` 与 `provider.steamid`。**
`player_id.observer_slot` 可作为二重保险。

这既是必须防的坑，也是"评论队友操作"这个功能的数据来源——
观战期拿到的正是你此刻正在看的那名队友的完整状态。
但拿不到 `allplayers_*`，所以只能评论正在观看的那一个人，无法评论全队。

### previously / added 是健康信号

游戏在推送完整状态的同时，会附带 `previously`（变化字段的旧值）与 `added`（新出现的字段）。

官方文档指出：**如果端点从来收不到这两个块，说明游戏一直没拿到 HTTP 2XX 响应，
把每次请求都当成失败了。**

因此这两个块的存在可作为"接收链路健康"的判据。
我们的主判据仍是自行比对前后快照（可应对后端重启与丢包），
`previously` 作为交叉验证手段。

### 推送节奏（实测）

- 状态有变化时：中位间隔 0.314 秒，约 3 Hz；最短 0.208 秒
- 静置时：约 30 秒一次心跳
- 配置的 `throttle` 0.1 秒决定了理论上限约 10 Hz
- 游戏在上一个请求未收到响应前不会发下一个，因此端点必须快速返回
  （我们实测中位 1.6 毫秒、P95 2.2 毫秒）

## 三、我们能推出什么

### A. 单张快照直接可读

- 当前模式、地图、回合数、双方比分、比赛阶段（热身/进行中/结束）
- 你在 CT 还是 T
- 血量、护甲、有无头盔、有无拆弹器
- 手持武器、弹夹余弹、备弹
- 身上金钱、装备总价值
- 被闪强度、身处烟雾、正在燃烧（均为 0–255 强度值）
- 炸弹是否已安放 / 已拆除 / 已爆炸
- **你的队伍连败了几个回合**
- 剩余暂停次数
- 全场累计击杀、助攻、死亡、MVP、评分

### B. 靠比对前后快照可得（M2-T3 的核心工作）

| 事件 | 判据 |
|---|---|
| 击杀 | 本回合击杀数增加 |
| 爆头击杀 | 本回合爆头数同步增加 |
| 多杀 | 一次增加 ≥2，或一回合内累计达到阈值 |
| 死亡 | 血量归零，或全场死亡数增加 |
| 助攻 | 全场助攻数增加 |
| 拿到 MVP | 全场 MVP 数增加 |
| 回合胜负 | 回合获胜方出现 + 比分变化 |
| 买了装备 | 金钱骤降 + 装备价值上升 |
| 换枪 | 手持武器变化 |
| 捡枪 / 掉枪 | 武器列表增删 |
| 被闪 | 被闪强度从 0 变大 |
| 中燃烧弹 | 燃烧值从 0 变大 |
| 掉血但活着 | 血量下降且未归零 |
| 经济崩溃 | 金钱与装备价值同时处于低位 |
| 换边 | 队伍标识变化 |
| 连败加深 | 连败计数增加 |

### C-2. 局势判断能做到什么（M2-T5 实测反馈引出）

可以做：
- 比分态势：领先 / 落后 / 追平 / 赛点 / 悬殊（来自 map.team_ct.score 与 team_t.score）
- 队伍连败轮数（map.team_ct.consecutive_round_losses，需在 GameSnapshot 中补充解析）
- 自己的经济状况（money、equip_value）
- 本回合自己已有几个击杀

做不到：
- 场上双方存活人数、残局判断。这是 allplayers_* 的限制，没有可靠替代。
  存在一个不精确的近似（本人存活 + 回合已进行较久 + 本回合有击杀），
  但它同样会命中憋大的 eco 局，误报代价高于收益，暂不采用。

### C. 靠我们自行计时可得

- **本回合存活时间**：从回合进入 live 到血量归零。
  这是"白给"事件的主要判据，因为官方的回合倒计时对普通玩家不开放
- 开局到首次击杀/首次掉血的间隔
- 单局总时长、连续游戏时长
- 长时间无任何状态变化 → 疑似挂机

### D. 做不到

| 想要的 | 为什么做不到 |
|---|---|
| **谁杀了你** | GSI 不提供击杀者信息。需要读屏幕上的击杀提示（M5） |
| 全场首杀 | 看不到其他玩家的数据 |
| 你打出了多少伤害 | `round_totaldmg` 在实测的 119 条样本中始终缺失，M2-T2 已确认 CS2 不提供 |
| **场上双方还剩几个人** | 需要 `allplayers_*`，仅 GOTV/观察者可用。死亡观战期间实测同样为 0 次 |
| **是否处于残局（1vN）** | 同上。这是数据层面的硬限制，无法通过任何推断可靠得到 |
| **谁拆的包、谁引爆的** | GSI 只给"哪一方以何种方式获胜"，不给具体执行者 |
| **你在地图上的哪个点位** | 需要 `player_position`，仅观察者可用。因此话术中不得出现任何点位称呼 |
| 敌人 / 队友位置 | 需要观察者身份 |
| 你的准星朝向、正在看哪里 | 同上 |
| 网络延迟、掉线 | GSI 不提供 |
| 语音聊天内容 | GSI 不提供 |
| 回合剩余时间 | `phase_countdowns` 仅观察者可用 |

## 四、待确认项

1. ~~`round_totaldmg` 是否存在~~ 已确认：CS2 休闲模式不提供，原始数据中字段名出现 0 次。
2. `phase_countdowns` 在休闲模式下对普通玩家是否真的完全无效。
   代价极低：加进配置文件，看一次 payload 即可。
3. `bomb` 数据组对普通玩家是否产出任何内容。
   若无，应从配置文件中移除，避免请求无用数据。
4. 死亡观战期间，`allplayers_*` 是否会生效。
   若会，评论队友的能力将从"只能评论正在观看的一人"扩展到"全队"。
