# OCR 完整流程说明

## 这条管线解决什么问题

OCR 是“光学字符识别”，作用是把游戏画面里能看见的文字、数字和它们所在的位置转换成可追溯的本地证据。它是常驻传感器，不负责判断文字是否为事实，也不会把识别结果直接发给在线模型。

当前生产配置固定使用 PP-OCRv6 tiny 检测器与识别器、OpenVINO CPU 引擎、两个推理线程、检测器边长上限 1280，以及简体中文语言配置。模型文件只从配置指定的本地目录读取。该配置来自 AGENTS.md §5.4 的定型测试：在四十帧严格答案集上识别到 270/324 行，严格召回为 83.3%。

## 一帧画面如何进入 OCR

Windows Graphics Capture 先从目标游戏窗口取得一帧内存位图。画面变化检测器随后判断这帧是否值得处理。检测器确认有变化的帧会进入 OCR；为了在长时间静止时仍能定期确认状态，心跳帧也会进入 OCR。

普通的 `no_change` 帧会被跳过。它表示检测器没有发现值得上传的画面变化，这类帧上的文字也没有变化，因此重复识别只会消耗 CPU。B-T4b 离线重放共抓取 2150 帧，其中 OCR 处理 1126 帧、跳过 1024 帧，跳过率为 47.6%；数据来自 `eval-reports/m5-b-t4b-minimal/report.md`。

被检测器选中的帧和心跳帧遵循同一条 OCR 路径。检测器是否提供局部聚焦区域不会改变 OCR 范围，当前 OCR 始终读取整帧。

## 内存输入和后台执行

OCR 直接读取截屏产生的内存像素，不先写成 PNG、JPEG 或其他图片文件，也不经过上传。画面的颜色通道在内存中转换成引擎需要的顺序，然后交给 OCR 工作线程。

工作线程与快线模型调用相互独立，因此 OCR 不会阻塞下一帧派发。OCR 工作线程在 Windows 上使用低于普通线程的优先级，让游戏和前台工作优先获得 CPU。OpenVINO 内部使用配置指定的两个推理线程；外层只有一个 OCR 工作线程，所以同一时刻只执行一次识别。

引擎在会话开始时创建一次，并用空白画面完成预热。方向分类阶段关闭，不会构造或运行文字方向分类器。每次识别同时记录总耗时、文字检测耗时、文字识别耗时和进程 CPU 核心秒数。

## 忙碌、迟到与失败

如果新帧到达时上一次 OCR 仍在运行，新帧会记录为 `late`，不会进入等待队列，也不会重试。已经运行的工作超过一个轮询周期时，同样把本帧记录为 `late`；迟到结果不会补写文字，也不会推进文字缓存。这样可以避免旧画面在后来覆盖新画面的时间线。B-T4b 的四段离线重放和三段启用 OCR 的文明 6 实机资源测试都记录到零次 `late`，来源分别是两份 B-T4b 评测报告。

如果模型文件缺失、依赖不可用或引擎启动失败，系统会记录一次错误，本会话关闭 OCR，然后继续运行其余视觉管线。模型文件不存在时直接抛出本地文件缺失错误，不触发下载。

如果单帧识别失败，该帧会留下结果为 `failed` 的帧级证据，不产生文字证据，也不更新文字差分状态。关闭 OCR 配置时不创建引擎，也不产生 OCR 证据。

## 识别结果如何变成行差分

OCR 返回每一行的文字、位置四边形和引擎置信度。位置使用画面宽高归一化，因此不同分辨率下仍处于零到一的统一坐标范围。文字行缓存会把当前帧与上一张成功完成 OCR 的帧按文字内容和邻近位置配对，再生成四种 `change`：

- `new` 表示当前位置出现了上一张成功 OCR 帧中没有的文字，`streak` 从首次观察开始计数。
- `stable` 表示同一位置继续读到同一文字，`streak` 表示连续成功 OCR 帧中读到它的次数。
- `changed` 表示同一位置的文字内容改变，`previous_text` 保存改变前的文字，新的 `streak` 重新开始。
- `gone` 表示上一张成功 OCR 帧中的文字在当前帧不再出现，位置和 `streak` 保留消失前的最后记录。

被跳过的 `no_change` 帧和 `late` 帧都不会清空缓存，也不会增加 `streak`。只有成功完成的 OCR 帧参与差分。

## 两种 OCR 证据

所有结果以 JSON Lines 形式追加到会话目录的 `evidence.jsonl`。JSON Lines 表示文件中每一行都是一条独立 JSON 记录，记录只追加、不回写。

`ocr_frame` 是一次帧级执行记录。公共证据字段说明它属于哪一帧、画面发生时刻和系统得知时刻；载荷字段包括引擎名称、推理线程数、检测器边长上限、识别行数、总耗时、检测耗时、识别耗时、CPU 核心秒数、触发来源，以及 `ok`、`late` 或 `failed` 的执行结果。

`text_observed` 是一条文字行证据。同一帧可以有多条。公共证据字段仍指向源帧；载荷字段包括文字、归一化外接框、四点位置、`change`、改变前文字、`streak`、引擎名称和引擎置信度。OCR 输出是证词而不是已经确认的事实，后续信念层会利用跨帧一致性裁决它。

OCR 证据不会写进供人阅读的快线观察正文，也不会直接改变快线提示词。它与快线观察共享源帧编号，因此之后可以沿证据编号追溯到同一张画面。

## 当前已知局限

当前配置在四十帧严格答案集上的召回为 270/324，也就是 83.3%，不是全部可见文字都能读到。分类结果中 HUD 数字召回为 60.3%，是当前最弱类别；数字来自 AGENTS.md §5.4。

文明 6 的分段资源测试观察到 OCR 能跟上节奏，但开启与关闭段不是同一帧序列，环境波动大于待测效应。因此 OCR 对游戏帧时间和 1% low 的实际影响尚未实测，不能根据现有数据宣称有影响或没有影响。该事实来自 `eval-reports/m5-b-t4b-ingame/report.md` 与 AGENTS.md §5.4。

## 怎么自己检查它在工作

打开当前会话目录中的 `evidence.jsonl`，搜索 `"source":"ocr"`；如果文件使用带空格的 JSON 格式，也可以直接搜索 `"ocr"`。

先看 `kind` 为 `ocr_frame` 的记录。正常运行时，`trigger` 应为 `detector` 或 `heartbeat`，`outcome_detail` 通常为 `ok`，`recognized_line_count` 表示该帧识别出的行数，`elapsed_ms`、`det_ms`、`rec_ms` 和 `cpu_core_seconds` 应为非负值。画面没有文字时，成功记录的行数可以为零。

再看紧随成功帧记录出现的 `text_observed`。正常结果应包含非空 `text`、零到一范围内的 `bbox`、四种合法 `change` 之一，以及不小于首次观察计数的 `streak`。连续相同画面通常会看到 `stable` 和递增的 `streak`；界面文字改变时会看到 `changed`，并带有 `previous_text`。

如果只有 `ocr_frame` 的 `late` 或 `failed` 而没有对应的 `text_observed`，说明该帧按设计没有更新文字缓存。若整个会话都没有 OCR 记录，应检查启动日志是否报告模型文件、依赖或 OCR 配置不可用。
